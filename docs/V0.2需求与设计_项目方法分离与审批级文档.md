# MethodFlow V0.2 需求与设计

用户反馈（原话归纳）：
1. 项目（Project）和方法（Method）要分开，现在混在一起。
2. 方法开发模板要更成熟：网页填写后能导出 Word / PDF，直接用于审批。
3. （答复）系统无预设密码；首次访问时由用户创建管理员。

## A. 项目 / 方法分离

**概念**
- **项目（Project）**：产品/管线层面的工作容器，例如“XX-CAR-T 分析方法包”。有编号 `PRJ-YYYY-NNN`、名称、产品、适应症/阶段、起止日期、状态（进行中/暂停/完成/归档）、项目负责人、项目团队（成员）。一个项目下有 0..N 个方法。
- **方法（Method）**：一个具体的分析方法，例如“CD19/CD22 双靶点 CAR 流式检测法”。有编号 `AM-YYYY-NNN`（全局序号）、名称、所属项目、技术类型（模板）、被测属性、样品基质、预期用途、方法版本（如 V0.1 开发中）、生命周期（开发 development / 验证 validation / 转移 transfer / 常规使用 routine / 停用 retired；V0.2 只有开发流程，其余生命周期阶段作为状态字段手动记录并写审计，流程模板留待后续）、方法负责人、方法团队、开发工作状态（进行中/完成/归档/取消）。
- 原先“项目”承载的 9 阶段开发流程、实验、附件、评审、审计、文档，全部归属**方法**。

**数据模型 v2**（SCHEMA_VERSION=2；无需迁移旧数据，开发期数据可丢弃，但 `init_db` 要有版本检测：遇到 v1 库给出清晰错误并提示备份后删除/迁移工具）
- `projects(id, code, name, product, indication, phase, description, status, planned_start, planned_end, owner_id, created_by, created_at, updated_at)`
- `project_members(project_id, user_id, role)`，role ∈ owner / member / viewer。
- `methods(id, code, project_id, name, technique, template_key, template_version, analyte, matrix, intended_use, phase, method_version, lifecycle, status, planned_start, planned_end, owner_id, created_by, created_at, updated_at, meta)`
- `method_members(method_id, user_id, role)`，role ∈ owner / author / reviewer / approver / viewer（沿用原项目成员角色及全部职责分离规则）。方法成员必须是所属项目成员（admin 除外）。
- `stages / experiments / attachments / generated_docs`：`project_id` → `method_id`。`audit_log` 同时有 `project_id` 与 `method_id`（均可空）。`stage_revisions`、`reviews` 不变（经 stage_id）。
- 权限：查看方法 = 方法成员 ∪ 项目成员（任意角色）∪ admin；编辑/签署只看方法成员角色（含原有职责分离、全局角色匹配、contributors 规则）；项目负责人可管理项目成员、可创建方法、可调整方法成员；方法负责人调整本方法成员（仅限项目成员）。创建方法需要项目 owner/member 且全局角色含 author（或 admin）。
- 编号：`PRJ-2026-001`、`AM-2026-001`。克隆方法：可在同项目或另一项目（目标项目成员权限同创建）。

**API v2**（旧的 `/api/projects/{pid}/stages|experiments|attachments|audit|kb|docs|export|members|clone` 全部改为 `/api/methods/{mid}/...`）
- 项目：`GET/POST /api/projects`，`GET/PATCH /api/projects/{pid}`，`PUT /api/projects/{pid}/members`，`GET /api/projects/{pid}/methods`，`POST /api/projects/{pid}/methods`（创建方法，体含 name、template_key、analyte、matrix、intended_use、phase、planned_start、成员 [{user_id,role}]），`GET /api/projects/{pid}/audit`（项目级聚合审计）。
- 方法：`GET /api/methods`（我可见的全部，支持 q/status/project_id/technique/lifecycle 查询参数），`GET/PATCH /api/methods/{mid}`，`PUT /api/methods/{mid}/members`，`POST /api/methods/{mid}/clone`（{title, project_id?}），`POST /api/methods/{mid}/lifecycle`（{lifecycle, reason, password} 需方法负责人/批准人，写审计），`GET /api/methods/{mid}/export`。
- 阶段/实验/附件/审计/KB/文档：路径把 `/api/projects/{pid}/` 换成 `/api/methods/{mid}/`，其余不变（含 review 必须带 revision 与 expected_hash）。`/api/experiments/{eid}`、`/api/attachments/{aid}/...`、`/api/docs/{did}/download` 不变。
- `GET /api/dashboard`：`{projects:[{id,code,name,product,status,my_roles,method_count,progress,overdue,stale}], methods:[{id,code,name,project_id,project_code,project_name,technique,lifecycle,status,progress,current_stage,overdue,stale,my_roles}], to_review, my_stages, my_experiments}`，待办条目含 `method_id/method_code/method/project_code`。
- 返回体里“project_*”字段若原本指方法，改为 `method_*`；detail 返回包含 `project: {id,code,name}` 摘要。

**前端 v2**
- 导航：工作台 / 项目 / 方法 / 知识库 / 管理。
- 路由：`/projects`（列表）、`/projects/new`、`/pr/:pid`（项目页：信息、团队、方法清单表含进度/当前阶段/风险提示、新增方法按钮、项目级审计标签）、`/methods`（全部方法，筛选）、`/methods/new?project=ID`（选模板、基本信息、成员，只能从项目成员选）、`/m/:mid`（方法总览，即原 `/p/:pid`）、`/m/:mid/stage/:key`、`/m/:mid/experiments`、`/m/:mid/exp/:eid`、`/m/:mid/docs`、`/m/:mid/audit`、`/m/:mid/kb`；`/kb`、`/admin` 不变。面包屑：项目 › PRJ… › 方法 AM…。
- 方法头部显示：方法编号/名称、所属项目（链接）、技术模板与版本、生命周期徽标、方法版本、开发状态。
- 旧路由 `/p/...` 不再保留。

## B. 模板成熟化（内容工程）

目标：一份模板 = 一份可直接用于审批的《分析方法开发方案》和《分析方法开发报告》的完整结构，符合制药行业受控文件习惯（参考 ICH Q14/Q2(R2)、FDA 2015 分析程序指南、FDA 2024 CAR-T 指南、USP <1220>、企业常见 SOP/方案模板）。不新增章节类型（text / fields / table / matrix / fmea 已够用），但各阶段章节要重新规划、补全，技术特定内容要更专业；可以新增 `list`-style 用 table 实现。
要求：
- **方案文档结构**（plan 文档由 charter–plan 阶段生成，章节编号稳定）：1 目的与范围；2 适用对象与职责（RACI 表）；3 缩略语与术语（表）；4 参考文件/法规依据（表，含文件编号/版本）；5 背景与研发目标；6 分析目标概况 ATP（用途、属性与规格、报告范围、性能特性与判据）；7 技术选择与方法原理（评分矩阵、方法原理描述、初始方法条件/参数表）；8 材料、试剂、参比品与仪器（表，含供应商/规格/批号/效期/关键性/再确认计划）；9 样品与基质（样品类型、取样、保存、稳定性要求）；10 风险评估（石川图要点 + FMEA）；11 开发策略与实验设计（分阶段计划、每个实验的目的/设计/样本量/判据/决策规则、统计分析计划）；12 数据处理、可追溯性与数据完整性（软件/版本、原始数据保存、ALCOA）；13 偏离与变更处理；14 进度计划与里程碑；15 方案批准记录。
- **报告文档结构**：在上述基础上增加 摘要与结论、各实验结果汇总、稳健性/DoE 结果与 MODR/PAR、控制策略（SST、参比品、试剂再确认）、方法描述草稿（可转 SOP 的“操作步骤”章节：原理、试剂、仪器、样品制备、仪器设置、操作步骤、结果计算、可报告结果、SST 与接受标准、注意事项）、偏离清单、遗留问题与后续（验证建议）、结论与批准。
- 每个技术模板（flow/hplc/bioassay/qpcr/elisa/generic）都要有专业的预置内容：术语表默认项、参考文件默认项、关键试剂与仪器默认行、初始方法条件表（该技术的典型参数）、FMEA 种子（≥10 条，含 S/O/D 初值与控制措施建议）、实验种子（≥8 个，覆盖特异性/范围/线性/精密度/稳健性/稳定性/参比品/SST 等，含设计与接受判据示例，标注“示例值，须按 ATP 确认”）、ATP 判据行、SST 种子、检查清单（含引用条款）。流式模板保留已有 CAR 双靶点经验（串色、FMO、事件数、保持时间、Fc 受体、WRM 等）。HPLC：色谱条件、系统适用性、强制降解、峰纯度、基线/积分规则；生物活性：参考品、平行线/四参数、相对效力、PAR；qPCR：标准曲线/效率、NTC、抑制对照、LOD/LOQ；ELISA：包被/封闭/曲线拟合、平行性、钩状效应。
- 另外新增一个模板 `cell_based`（细胞法功能/效力测定），共 7 个。
- 文本类章节提供 `placeholder` 示例句，并在 `help` 中说明写作要点；必填项标记合理（不要全必填，也不要全选填）。
- 知识库补充：把“如何写好每一章”的要点、常见审评缺陷（deficiency）、检查清单对应条款追加到 kb_seed.py（≥30 条新增），来源标注准确，**不得编造法规条文号**；不确定的条款写“参见 xx 指南相应章节”并标记“待核对”。
- 模板版本号升到 `1.1`，每个模板含 `changelog`。

## C. 审批级文档导出（Word / PDF）

- 受控文件外观：页眉（公司名称占位可在系统设置中配置、文件名称、文件编号 `方法编号-PLAN-Vn`/`-RPT-Vn`、版本、状态），页脚（页码 X/Y、“打印件未经控制”或配置文字、生成时间），封面（文件标题、方法名称/编号、所属项目、版本、生效/批准日期、状态、编制/复核/批准姓名与日期表），修订历史表（来自文档版本与阶段修订及重新打开原因），目录（Word 字段 TOC，可更新；LibreOffice 转 PDF 时生成静态目录页），正文章节编号稳定（与模板结构一致），所有表格有表头重复、边框一致、列宽合理，图（甘特、FMEA 风险矩阵/排序）清晰，附录（检查清单、实验结果汇总、附件清单含 SHA-256 前 12 位、引用依据）。
- 签署页：按评审门列出：签署角色、姓名、签署含义、日期时间、修订号、数据哈希前 12 位、签名完整性状态。未批准阶段在文档中以水印或红色“草稿”标识，页眉显示“草稿—不得作为批准文件使用”；签名完整性失败显示“完整性校验失败”。
- 导出格式：`.docx`（主）+ `.pdf`（经 LibreOffice `soffice --headless --convert-to pdf`，自动查找 `config.json` 的 `soffice_path`、PATH、`C:\Program Files\LibreOffice\program\soffice.exe`；未找到则 PDF 按钮置灰并提示安装方法，不影响 Word）。PDF 与对应 docx 同名，记录到 generated_docs（含 `format` 字段），一次生成同时产出两者。
- 中文字体：Word 用微软雅黑/宋体；PDF 转换需系统有中文字体（Windows 有）；图表字体使用 matplotlib 可用中文字体并回退。
- 文档数据来源完全是方法的阶段数据（模板驱动，章节顺序按模板而非硬编码），用户在网页填写的内容原样进入文档，不丢项；空必填章节在草稿里以“【待填写】”高亮。
- 设置：`/api/admin/settings`（admin）可配置 公司名称、文件页脚文字、文件编号前缀、soffice_path；写审计。
