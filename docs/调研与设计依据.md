# MethodFlow 调研与设计依据

日期：2026-10-14　状态：V0.1（随程序迭代更新）

## 1. 目标（来自需求）
1. 规范化管理**分析方法开发**的流程、进度与结果，并能**生成规范的方法开发方案文档**。
2. **关键阶段必须复核**（评审门，stage-gate）。
3. 网页版，且有**记忆能力、存储能力**（跨会话、跨用户的持久化；可追溯）。
4. “基于学习经验”：把本次工作中沉淀的方法开发知识（模板、检查清单、风险库、常见陷阱）固化到程序里，并能随项目积累新经验。

## 2. 调研结论与对设计的约束

| 来源 | 结论 | 对设计的约束 |
|---|---|---|
| FDA《Part 11 范围与适用》（2003 指南）与 21 CFR 11（§11.10、Subpart C，细则以 eCFR 为准） | 只要用电子方式保存、审核并批准记录，就应满足：受控访问、**计算机生成并带时间戳的审计追踪**（记录操作及修改前的值）、电子签名唯一、签名含**姓名/日期时间/含义**并与记录**绑定** | 全部写入操作进入审计；审计表**只追加**并用**哈希链**做篡改检测；签名重新输入口令，签名记录含数据哈希；签后数据变化可被发现 |
| FDA《数据完整性与 CGMP 问答》（2018） | 数据应可归属、清晰、同步、原始、准确（ALCOA）；审计追踪应按风险**定期审核**；访问需限制 | 每条记录带作者与时间；管理页提供审计追踪浏览与链校验；角色权限分离 |
| ICH Q14 / Q2(R2) | ATP 驱动开发；风险评估；DoE；控制策略；变更管理 | 模板阶段按 ATP → 技术选择 → 风险评估 → 方案 → 实验 → 稳健性 → 控制策略 → 报告组织；ATP 等结构化字段 |
| USP <1220>（生命周期三阶段：设计 / 性能确认 / 持续验证，ATP 居中） | 开发是生命周期第 1 阶段，后续验证/转移/监控沿用同一 ATP | 数据模型与阶段模板可扩展；本版先覆盖“开发”，预留“验证/转移/监控”模板 |
| GAMP 5（第二版）：自研软件属最高风险类别 | 需要需求、设计、测试证据；基于风险的保证 | 提供 URS、测试用例与自动测试报告；**文档明确：本程序是辅助工具，用于 GxP 前须按企业 CSV 流程验证** |
| 本次交付沉淀的经验（指导文件 V2.0、CAR 流式案例、FMEA、门评审清单） | 阶段与门的设置、风险库、陷阱库、检查清单已成体系 | 作为内置模板与知识库种子 |
| 已有软件调研（Fusion QbD、Empower MVM、Kneat、ValGenesis、LIMS/ELN 等） | 现成产品偏色谱或偏验证文档管理，缺少“方法开发方案—实验—复核—文档”一体的轻量工具 | 自建轻量系统，聚焦开发流程；不替代 LIMS/ELN/CDS |

## 3. 架构决策
- **后端**：Python（FastAPI + uvicorn）+ **SQLite（WAL）**，数据存 `data\`；附件存磁盘并记录 SHA-256；**自动与手动备份**。
- **前端**：无需构建的单页应用（原生 JS），浏览器访问 `http://127.0.0.1:8780`。默认只监听本机；局域网使用需配置并加 HTTPS 反向代理（见 README）。
- **记忆与存储**：所有项目、阶段内容、实验、附件、复核、审计、知识库均持久化；阶段在提交复核时形成**版本快照**；项目可克隆；完成项目时可把**经验教训**写入知识库，新项目按技术类型自动推送相关知识。
- **复核（评审门）**：状态机 `未开始 → 进行中 → 待复核 → 通过/退回`；复核人与批准人**不得是该版本的编辑者**，且彼此不同；退回需写原因；通过后阶段**锁定**；重新打开需写原因并使后续已批准的门**失效**。
- **文档生成**：python-docx 生成《方法开发方案》（计划阶段）与《方法开发报告》（含结果）；文档带状态横幅（含未复核内容时标“草稿”）、签名页（复核/批准的姓名、时间、含义、数据哈希）、甘特图、FMEA 图、附件清单。

## 4. 范围与局限（V0.1）
- 覆盖：方法开发（生命周期第 1 阶段）。验证、转移、持续监控的模板留作后续版本。
- 本地账号体系（bcrypt、锁定、会话）；未对接企业 SSO。
- 电子签名为**程序内签名**（重新认证 + 记录绑定），是否满足企业的 Part 11 / Annex 11 要求，须由 QA 按 CSV 流程评估。
- 统计计算器仅在知识库中提供链接/说明，数值计算请用 MethodLab 或验证过的统计软件。
